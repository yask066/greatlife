# Публикация «Прекрасной жизни» на hoster.by

Инструкция относится к статической сборке Astro. На hoster.by загружается
только содержимое `dist/`; Node.js, исходники и `node_modules` на сервере не
нужны.

> Состояние инструкции: проверено по открытой базе знаний hoster.by
> 22.09.2026. Перед публикацией повторно сверить названия пунктов в личном
> кабинете: hoster.by переводит услуги между панелями, а конкретный документный
> корень зависит от домена и аккаунта.

## 1. Подготовить production-сборку

1. Получить подтверждённые контакты, профили, фотографии и редакционные тексты.
   Все пункты в [чеклисте согласования](./content-approval.md) должны быть
   отмечены `[x]`. Пока в данных остаётся `approval: 'demo'` или не хватает
   согласия, production gate обязан остановить публикацию.
2. В локальной копии проекта указать настоящий canonical URL без завершающего
   `/`. В примере ниже выбран вариант без `www`; если владелец домена выбирает
   `www`, заменить значение во всех шагах на `https://www.example.by`.

   ```powershell
   $env:SITE_URL = 'https://example.by'
   npm ci
   npm run release:check
   ```

   Команда `release:check` запускает production gate, проверку типов и сборку,
   unit/e2e-тесты, проверку файлов `dist` и Lighthouse. Не загружать артефакт,
   если команда завершилась с ошибкой.

3. Перед передачей файлов убедиться, что в `dist/` лежат `index.html`,
   `robots.txt`, `sitemap.xml`, favicon, шрифт и остальные ресурсы, а ссылки
   в HTML не ведут на `example.invalid` или демонстрационные контакты.

## 2. Загрузить только `dist/`

1. В личном кабинете hoster.by открыть услугу виртуального хостинга и панель
   `ISPmanager`.
2. В разделе **Сайты** посмотреть значение **Корневая директория** именно у
   рабочего домена. Для обычного UNIX-хостинга hoster.by описывает
   `public_html/` как главный каталог сайта и символическую ссылку `www/` на
   него; фактическое значение в аккаунте имеет приоритет.
3. Сделать резервную копию текущего сайта. Затем скопировать файлы и папки из
   `dist/` в этот document root с сохранением структуры. Файл `index.html`
   должен находиться непосредственно в корне сайта, не в дополнительной папке
   `dist/`.
4. Не загружать на хостинг `src/`, `public/`, `tests/`, `docs/`, `.git/`,
   `node_modules/`, `package.json`, `package-lock.json`, конфигурацию Astro и
   файлы тестовых отчётов.

## 3. Включить HTTPS

В актуальной инструкции hoster.by для UNIX-хостинга указано, что сертификат
Let's Encrypt выпускается в ISPmanager через **Безопасность → Lets Encrypt
SSL** и автоматически продлевается. Для рабочего домена:

1. Убедиться, что DNS домена и `www` (если он будет перенаправляться) уже
   указывают на hoster.by.
2. В ISPmanager открыть **Сайты**, выбрать домен и перейти в
   **Безопасность → Lets Encrypt SSL**.
3. Выпустить сертификат для тех имён, которые реально обслуживаются до
   редиректа: canonical host и второй host (`www` или без `www`). Набор
   флажков сверить с текущей формой панели; не оставлять второй host без
   сертификата, если проверка должна начинаться с `https://`.
4. Подождать применение сертификата и проверить оба HTTPS-адреса. Если раздел
   или кнопка недоступны, не устанавливать сертификат вручную: обратиться в
   поддержку hoster.by и зафиксировать результат в чеклисте публикации.

## 4. Выбрать один canonical host и настроить 301

Для этого проекта по умолчанию используется canonical-версия без `www`:

```text
https://example.by
```

Фактический домен должен заменить `example.by` до сборки. Значение в
`SITE_URL`, canonical в HTML, sitemap, robots и адрес назначения редиректа
должны совпадать.

Для HTTPS-редиректа использовать проверенный для hoster.by путь ISPmanager:

1. В ISPmanager открыть **Сайты**.
2. У нужного сайта открыть контекстное меню и выбрать **Настройки
   редиректов**.
3. Нажать **Создать редирект**.
4. Заполнить форму:

   ```text
   Код ответа сервера: 301 Moved Permanently
   Путь страницы: /
   URL назначения: https://example.by/
   ```

   В официальной инструкции hoster.by путь начинается с `/`, а внешний URL —
   с `http://` или `https://`. Для правила на весь домен в текущей панели
   включить режим, сохраняющий хвост пути запроса; если такого режима нет,
   сначала проверить редирект для `/robots.txt`, `/sitemap.xml` и произвольного
   пути. Не публиковать правило, которое отправляет только главную страницу и
   оставляет остальные пути на втором host.
5. Сохранить правило и убедиться, что на втором host не осталось отдельной
   копии сайта. Для варианта canonical с `www` поменять местами источник и
   URL назначения.

Не добавлять `.htaccess`, nginx-конфигурацию или другой серверный фрагмент по
памяти: конкретный веб-сервер и права конфигурации определяются аккаунтом. Если
в установленной панели нет описанного режима для host-wide редиректа, получить
подтверждённую схему у поддержки hoster.by и записать её здесь перед
публикацией.

## 5. Проверить публикацию

Подставить реальный домен и проверить, что нет цепочки редиректов:

```powershell
curl.exe -I http://example.by/
curl.exe -I http://www.example.by/
curl.exe -I https://www.example.by/
curl.exe -I https://example.by/
curl.exe -I https://example.by/robots.txt
curl.exe -I https://example.by/sitemap.xml
```

Ожидаемый результат:

- HTTP и неканонический host отвечают одним `301` на `https://example.by` с
  сохранением пути запроса;
- canonical URL отвечает `200 OK` по HTTPS;
- `robots.txt` и `sitemap.xml` доступны по canonical host;
- в HTML canonical, JSON-LD, robots и sitemap используют тот же host;
- hash-ссылки `#speech`, `#psychology` и `#bowls` открывают страницу и
  выбирают соответствующее направление;
- телефон и Telegram ведут на подтверждённые значения;
- в консоли браузера нет ошибок, а Lighthouse для рабочего HTTPS URL даёт не
  менее 90 по Performance, Accessibility и SEO.

Проверять hash-ссылки и консоль в браузере после финальной загрузки; `curl` не
передаёт hash-фрагмент серверу.

## 6. Зафиксировать параметры публикации

Перед передачей проекта владельцу заполнить этот блок в задаче публикации или
в рабочем журнале, не добавляя сюда пароли и персональные данные:

```text
Домен: <реальный домен>
Canonical host: <без www | с www>
Document root в ISPmanager: <фактический путь>
Сертификат: <дата выпуска и покрытые hostnames>
Правило 301: <дата проверки и путь в ISPmanager>
Проверка URL: <дата, результат curl/Lighthouse>
```
